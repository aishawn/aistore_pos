# Reporting Design

Updated: 2026-11-05. Owner: TBD.

## Scope and data path

The reporting UI lives in `pos-ui`; report pages call same-origin `/api/odoo/*` routes. `reportAccess` enforces report permission and derives the company, warehouse, host, and timezone from the authenticated store binding. The API queries Odoo with company-scoped domains and returns uncached responses. Overview uses prepared snapshots and records Shopfront source coverage by target and business date; sales, purchases, and register closures query Odoo directly.

Report detail views expose store/company, period, source, timezone, generation time, and source coverage where it helps validate the result. Inventory includes the Shopfront Active catalog count, the complete source snapshot's positive quantity, negative-row count, and snapshot time next to Odoo's saleable-variant count. Shopfront and Odoo use different scopes; the source snapshot is read-only and older than 24 hours is explicitly marked stale. Overview keeps source coverage internal so an unconfirmed crawler event does not add noise to the dashboard. A null Shopfront sync record means coverage is unknown, not that synchronization failed or completed. The sync ledger records only days for which a sync event was recorded. It does not independently prove the Odoo mirror contains every source row.

The reporting navigation keeps operational workflows separate from analysis: Sales report, Sales History, Inventory, Purchase analysis, Purchase Orders, Transfers, and Register Closures. Purchase analysis is read-only and covers confirmed/done `purchase.order` amounts. Purchase Orders remains the workflow for confirmation and receiving; a confirmed order value does not imply goods were received or paid. The duplicate `Receipts · To receive` tab is removed; legacy `/purchases?state=purchase` links resolve to the canonical purchase-order list. Register Closures is an independent entry for closed `pos.session` records.

Sales, purchase, and register-closure reports share Today / Last 7 days / Last 30 days presets, custom store-date ranges, and previous-period / same-period-last-year comparisons. Sales groups by date, product, or POS category. Purchase analysis groups by supplier, status, date, or month; date and month buckets use the bound store timezone. Register Closures shows expected ending cash, counted ending cash, and `counted - expected`; Differences only filters non-zero cash variances. Inventory is a point-in-time report, not a date-range report: it supports all / zero / negative stock filters, sortable headers, and progressive loading. Its footer distinguishes loaded rows from all matching Odoo POS-enabled product variants; positive stock units sum only positive balances and do not offset negative stock, which remains separately flagged. Shopfront active-catalog counts use a different source and product scope, so they are not directly comparable. Shopfront sync coverage does not prove row-level completeness of the Odoo snapshot.

Sales group rows open a read-only source panel: date groups resolve to matching `pos.order` records, while product/category groups resolve to matching `pos.order.line` records. Purchase groups resolve to matching `purchase.order` records. Detail requests repeat the report's company/date/state scope, paginate source records, and calculate source amount minus the selected group amount. A non-zero difference is shown as a reconciliation signal, not hidden. Inventory report query, category, stock-status, sort, and visible-column state is stored in its URL; the inventory snapshot is a point-in-time Odoo read. Its CSV and print actions fetch all rows in the same snapshot and apply the selected visible columns. The inventory report does not expose stock value or product-edit actions.

## Metrics and boundaries

- Sales: completed POS orders (`paid`, `done`, `invoiced`) with positive order total. Negative-total refund orders are excluded; refund lines inside an otherwise positive order may remain. Date grouping counts orders and sums order totals. Product/category grouping reads sale lines, sums `qty` and `price_subtotal_incl`, and counts lines. Date grouping quantity is unknown and must display as `—`, never zero. The order gross total and grouped line amount are shown separately with their difference; line allocation is not represented as an accounting reconciliation.
- Sales category grouping uses the first POS category attached to a product; uncategorised products are explicit. Products with multiple POS categories are not fractionally attributed.
- Purchases: `purchase.order` records in `purchase` or `done`, grouped by supplier/status/month. `amount_total` is the confirmed order amount, not proof of invoice payment, goods received, or final accounting cost.
- Register closures: closed `pos.session` records, expected ending cash compared with counted ending cash. The difference is cash reconciliation only; it does not represent card settlement or total drawer variance. Exception filtering is evaluated across the selected range, capped at 10,000 rows.
- Inventory/dead stock: Odoo stock and cost data. Inventory uses the bound store warehouse/location and available POS products so the dashboard, product inventory and inventory dialog share a store scope. Invalid or missing quantity/cost and incomplete catalogue coverage must be disclosed; derived stock value is not realized savings.
- Shopfront historical sales are stored in the separate `shopfront.sync.sale` mirror. Odoo deliberately does not turn historical mirror rows into native `pos.order` records because that can trigger stock movements. Therefore source gross/tax and native POS gross/tax are separate ledgers and must not be compared or used to mark either ledger incomplete. Sync-event coverage remains separate from row completeness; native Odoo order totals reconcile only against their own order lines.

All date filters use the store timezone and half-open UTC intervals. No report page may imply a business write. CSV output must escape spreadsheet formula prefixes; selected columns must match the on-screen table while exports still include every matching row. Print output keeps the selected table columns and hides filter/tool controls. Filter state is URL-addressable where implemented. Large tables should report loaded and matching totals and make the export scope clear.

The Overview's sales KPI is net sales after refunds, including tax. Sales report totals use completed Odoo POS orders with positive order totals; negative-total refund orders are excluded, and product/category group totals come from sale lines. These numbers are intentionally not described as the same metric. The sales page identifies the scope and shows order-gross versus grouped-line reconciliation so a difference remains visible; a future accounting-grade net-sales view requires a verified refund/order allocation contract.

## Change controls

When a metric, state domain, date rule, or source changes, update this file and validation evidence. Keep historical reports immutable. Mark unobserved deployment and online behavior as NOT RUN.
