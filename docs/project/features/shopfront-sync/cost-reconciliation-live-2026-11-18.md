## Shopfront Cost Field Semantics

The public [Products object documentation](https://developer.onshopfront.com/documentation/Objects/Products) distinguishes the outlet's current case cost (affected by Vendor settings), the outlet's `lastCost` (last case cost), and the outlet's `averageCost`. It also defines the `Cost.cost` value as including tax. The [Cost Tax Rate ID documentation](https://developer.onshopfront.com/documentation/Types/Cost%20Tax%20Rate%20ID) says the `inherit` value uses the product's sale tax rate when handling cost. These are distinct fields and settings; do not treat current outlet cost, last case cost, and average case cost as interchangeable.

The public [Special Reports documentation](https://developer.onshopfront.com/documentation/Reporting/Special%20Reports) shows the Inventory At Date report returning both `Last Case Cost (Ex)` and `Last Case Cost`, plus stock values excluding and including tax. Its example reports `$12.50` ex tax and `$13.75` including tax. This documents the report API's paired fields, but does not prove that the signed-in `/reports/misc` page uses the same report, filters, or display settings.

## Barcode Reassignment Gate

The detailed classification contains 104 zero-stock stale-owner rows (52 per store). Every row's requested Shopfront product is `ACTIVE`, present in the current catalog, and declares the barcode. The existing POS owner is also `ACTIVE` and catalog-confirmed, has zero inventory, and no longer declares that barcode in its current source record. These rows are separate from the 202 source-side duplicate claims.

The POS importer previously allowed migration only when the old owner's source mapping was absent from the registered catalog snapshot and inventory was zero. This prevented a move when the old product remained active in Shopfront but no longer listed the barcode. Review also found that migration authorization was keyed by old product ID: a safe barcode on a multi-barcode owner could accidentally authorize a different duplicate-claimed barcode from the same owner. The implementation now authorizes each barcode code independently, requiring a registered complete fingerprinted snapshot, a unique current source claimant matching the incoming source ID, the target source ID in the snapshot, one mapped source for the old POS owner, and zero old-owner inventory.

Zero inventory alone is never sufficient authority to move the code. A permitted move uses the complete current source snapshot to prove exactly one Shopfront claimant; it updates only the outlet-scoped barcode association, records old/new product IDs and the evidence snapshot in an audit row, and leaves inventory, product status, cost, and historical sales untouched. The audit reason is `verified_unclaimed_shopfront_barcode`. Automated tests cover current-owner removal, retired owners, negative inventory, duplicate claims, and isolation between multiple barcodes on one owner. The code change is not yet deployed, and no live barcode was changed during this audit.

There was no active sync job at the time of the status query. The current source catalog observation is recent, while catalog job health is still partial/stale because the latest catalog job did not reach a clean terminal success.

## Barcode Migration Gate Root Cause and Production Verification

The POS `main` fix was deployed to SKR and Demo as `6144d9afd3c7be1104531c3aadb604f1999174a5`. The first post-deploy snapshot `#875` correctly persisted the complete Shopfront barcode snapshot, but no migration occurred. Read-only comparison of the strict run `#530` candidates against both POS outlets showed all 45 candidate owners per store met the database checks: active owner, zero inventory, no sale/order/receipt/movement/stocktake references, one old source mapping, one current Shopfront barcode claimant, and the barcode still assigned to the old owner.

The runtime cause was in the Crawler payload projection: `compact_business_payload()` dropped `catalog_snapshot_complete` and `catalog_snapshot_fingerprint` before sending each product to POS. Consequently, the POS migration gate correctly failed closed at `complete_snapshot_metadata` for all batches even though the fingerprinted snapshot had been registered separately. The Crawler fix added these two fields to the product allowlist while retaining private-field filtering. Regression tests first failed with the fields omitted, then passed after the fix.
