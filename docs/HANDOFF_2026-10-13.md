## 一、项目定位

Orithos POS 现在以 Odoo 作为商品、库存、销售、采购和 POS 会话的唯一业务事实源。Next.js 负责收银和后台交互，Spring Boot 负责认证、权限、Odoo 代理和 AI 能力。仓库里的 Classic MySQL POS 保留为行为参考和 AI 相关代码参考，默认不作为试点的可写数据源。

线上地址：

- Web：<https://app.orithos.com.au/>
- Odoo：<https://odoo.orithos.com.au/odoo/point-of-sale>
- Dokploy 服务：`aistorepos`，项目 `aistore`，环境 `production`

## 三、尚未完成或需要验收

### 1. Odoo 家具演示数据尚未删除

Odoo 商品列表中确认有 37 个家具/办公演示商品，包括桌子、椅子、柜子、沙发、白板和办公用品。已在 Odoo 列表中精确选中这 37 项并提交删除，但 Odoo 返回：

> To delete a product, make sure all point of sale sessions are closed.

当前 `orithos_store1` POS 会话仍处于打开状态。为避免替店主做关账或影响现金对账，没有自动关闭该会话。

交接操作：

1. 在 Odoo 完成当班销售和现金核对。
2. 在 Odoo POS 中关闭 `orithos_store1` 会话。
3. 回到 Odoo → Products，重新选择那 37 个家具/办公演示商品。
4. 执行 Actions → Delete；若 Odoo 仍因历史单据阻止删除，则使用 Archive，并确认 POS 商品筛选中不再显示。
5. 保留两款酒类演示商品，或在确认后再清理它们。

不要使用“Fresh Volumes”或删除数据库卷来清理 Odoo 数据，这会造成不可逆的数据损失。

### 3. AI 仍未启用

AI 代码已经存在，但生产环境的 `AI_ENABLED` 仍为 `false` 或缺少 DashScope Key。以下能力因此仍属于未验收状态：

- 收银助手文字问数和页面动作。
- 语音转文字。
- 发票图片 OCR。
- 酒标识别和侍酒推荐。

启用前要在 Dokploy 配置 `AI_ENABLED=true`、DashScope Key 和模型配置，然后先发送不含店铺数据的通用测试问题。启用后可能产生按量费用；真实销售和库存问题应在确认数据范围后再测。

### 4. 侍酒模块的数据源仍需统一

当前侍酒相关代码仍有 Classic MySQL 商品词典和酒类算法。试点要求推荐结果来自 Odoo 在售商品和库存，因此还需要：

- 将候选商品、库存和价格改为 Odoo 查询结果。
- 保留口味、产区、年份等匹配算法。
- 当 Odoo 无酒类属性时，明确显示“资料不足”，不能编造风味和库存。
- 用真实 Odoo 商品做一次推荐、相似酒款和更便宜/更高档选项验收。

### 5. 页面级业务验收还没有完成

当前完成的是路由壳和关键接口检查，不是逐个页面的完整人工验收。以下路径仍需按“打开页面 → 搜索/筛选 → 打开详情 → 返回 → 空状态/错误状态”逐一检查：

- 收银：搜索、分类、加购、包装系数、挂单、结账、退款、关班。
- 商品：Odoo 商品列表、详情、库存数量和价格显示。
- 客户：列表、搜索、详情以及销售关联。
- 采购：采购单、供应商、补货建议、审批生成草稿 RFQ。
- 报表：仪表盘、时间范围、空数据和权限边界。
- 设置：公司、门店、POS 集成、权限和登录失效。
- AI：关闭状态提示、启用后的错误回退、确认弹窗和审计记录。

## 四、仓库里的模拟数据说明

仓库模拟数据不等于线上 Odoo 商品：

- [seed.sql](../pos-api/src/main/resources/db/seed.sql)：Absolut Vodka、Bacardi Carta Blanca、Carlton Draught、GST、供应商、门店和客户样例。
- [seed_ai_report_testdata.sql](../pos-api/src/main/resources/db/seed_ai_report_testdata.sql)：用于 AI 报表的啤酒、可乐、测试威士忌、库存和模拟销售记录。
- 前端还有少量演示销售和代表性仪表盘内容。

仓库 SQL 没有家具演示商品；Odoo 中的家具来自 Odoo 自带/演示目录。因此清理 Odoo 家具不会被仓库重新导入。Classic MySQL 种子数据只在新建 Classic 数据库时执行，也不会自动同步到 Odoo。
