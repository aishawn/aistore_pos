## 实施与本地验证

- `/products/cost-reconciliation` 增加独立的 Shopfront 来源毛利查询和证据下载；不依赖未修复的 Odoo 成本账。需要已验证的 SKR 门店绑定和管理员权限。
- 原始 Sale JSON 中三笔订单明细完整，但标准化明细重复最后一行：`11f13aca541cdcb0bb8706718276c393`、`11f13accba04d9908bff06d264d7c5cf`、`11f14a9029bfba7aad5806a85b6f6d41`。来源报告直接验证原始行 ID 和金额，同时披露标准化差异。没有写回或删除这些订单。
- crawler 的旧行迁移改为每个 legacy 商品行只消费一次，防止同商品销售/退款两行复用同一 ORM 记录；重复同步回归测试验证数量与成本符号不丢失。此提交包含 POS 仓库中的 crawler 副本，不代表独立 crawler 服务已部署。
- Odoo 全量成本审计覆盖 303,839 行，生成原值、建议值、write_date 和阻断原因的修复清单；全部保持待审，不执行写回。原始扫描作为发现证据，执行前须用统一规则重新生成并复核目标。
- 原生账共 155,142 笔订单，141,124 笔订单税额与明细不平；294 笔来源完成订单未匹配原生订单。按 UUID 关联的原生订单中，817 笔来源状态为 INCOMPLETE、10 笔为 PARKED，不能直接作为来源已完成销售。另有 16 笔未关联来源，须先区分本系统原生交易与缺失导入，不删除。
- 修复全量选择漏掉仅退款商品、未税/税额逐行校验、无证据默认零值、部分范围发布毛利、未写回建议值被当作实际成本、退款原销售行及累计数量校验。
- 36 项相关单元测试、4 项 crawler 财务映射测试、TypeScript 与定向 ESLint 通过。UI fixture 检查 36 项通过，仅证明界面与访问保护，不替代上线业务验收。没有本地应用构建或 Maven，没有修改 `pos-api/`。

私有原始证据在隔离 checkout 的 `.local/margin-implementation/`：`source-history-company-5/history-index.json` 及 `.revalidation.json`、`history-company-5/`、`source-yesterday/`、`reporting-crosscheck/`。原始业务数据、登录状态及 dump 不入 Git。

## 仍需完成的工作

1. 来源历史成本只证明 Shopfront 当时记录的成本。采购发票、实际收货数量、采购税、箱规和期初成本若源端没有，不能通过重同步创造出来；持续列为缺证。
2. Odoo 当前计价方法为标准成本；不得以最近收货价替代历史标准成本，也不得混入 FIFO / AVCO。导入来源报表成本与会计成本认证必须分开。
3. 原生退款有大量缺少原销售行关联。先获取明确关联证据，再生成冲回清单；不得按同商品或相似金额猜测原单。
4. 旧 501,008,395 字节 dump 的哈希虽匹配旧清单，但完整读取及隔离恢复出现 EOF，不能标记恢复成功。已改用服务端 1,756,331,962 字节备份完成全库恢复，见下文；附件文件库与应用启动验收仍未完成。
5. 库存已有另一项精确范围修复：见 [库存修复证据](INVENTORY_REPLAY_REPAIR_2026-11-03.md)。剩余 3,340 个 REVIEW 差异、来源负库存及后续移动仍待对账，不能全部归零或删除。

## 对用户的操作建议

保持正常增量同步；不用再手工触发全量同步，也不要批量删除“看起来不对”的记录。优先使用来源毛利报表，查看来源差异及待核实成本。只有唯一 ID、完整原始证据、可恢复备份和目标复核均通过的差异，才可制作有回滚方式的定向补数/修复。同步、删除、库存修复不能互相替代。

## 税额定向修复清单（尚未执行）

新增 `scripts/cost-reconciliation.mjs --tax-only true`：只采集税额所需证据，单独标记快照用途，禁止把未采集采购记录解释为成本缺证。原始来源行必须有唯一 ID；商品、数量、含税额和明细对应关系必须唯一；订单与明细原始税额/含税额必须严格相等。即使差 0.01 也进入待查，不能自动分摊。输出包含原值、建议值、写入时间与快照哈希，始终 `executable:false`，不写成本、库存或销售账。

既有 12 个原生快照离线分析：155,142 笔订单中，106,397 笔通过逐单税额证据规则，其中 94,990 笔有税额或未税金额差异；48,745 笔待查。主要阻断项（可重叠）：行关联不唯一/缺失 33,299、来源订单与明细合计不同 21,634、明细不能一一对应 5,983、完成状态/来源身份不符 843。部分旧快照没有完整来源覆盖标记，执行前必须重新采集，不能把这些数视为已获准写回数量。

根因样本：订单头税额 0.73、含税 7.98，但两行 `tax_ids` 为空，未税/含税都分别为 4.49、3.49。商品税 176 是 10% GST，却为税外价配置，直接补入会增大含税额。事务内复制该税并明确含税计价后，税引擎算出未税 4.08、3.17、税 0.41、0.32。保存行税配置及经过计算的 subtotal，flush、清缓存、重新读取并再次调用税引擎均一致；数量、售价、成本保持不变。事务回滚后，新事务确认原值与原税关联全部恢复。

修正先前关于自动重算的假设：本次部署 Odoo 19 中，`price_subtotal` 与 `price_subtotal_incl` 均为 `store=true, compute=None`。不能只改 tax_ids 后期待 subtotal 自动更新；必须共同保存经税引擎验证的金额与税配置。该样本没有订单/会话会计分录，不证明其他历史订单无过账影响。复制税及两行测试均未提交；成本仍为原零值，不因此认证成本。
