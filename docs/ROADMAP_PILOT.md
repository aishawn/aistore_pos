## 产品目标

为澳洲独立酒类零售店提供简洁、可靠的 POS 和日常经营工作台：店员能快速完成收银，老板能掌握商品、库存、采购和销售，并逐步借助 AI 改善补货、定价和推荐。

### 试点目标

让一位店主和少量店员，在不重复录入、不污染正式业务账的前提下，完成一条可追踪的核心流程：

**登录 → 读取 Odoo 商品与库存 → 收银 → 订单/收据 → 销售历史 → 指定订单退款 → POS 班次关账**

Odoo 是业务数据唯一事实源。Orithos 负责简洁交互和增值能力，不与 Classic MySQL 双写。

## 产品方向与阶段目标（2026-10-13）

### 产品方向

把 Orithos 做成澳洲独立酒类门店每天愿意使用的简洁经营工作台：店员用它快速、准确地收银；老板用它看清库存、销售和采购；AI 在数据可靠、规则可解释的基础上提供建议和查询。现阶段重点是先把 Odoo 数据链路和交易闭环做扎实，再验证 AI 的实际价值，避免同时扩张功能面。

### 目标层级

1. **近期目标：可控试点**——一个门店、一个 POS、少量员工；核心销售及库存数据以 Odoo 为准，页面不展示会误导经营决策的模拟配置。
2. **中期目标：可日常运营**——商品/库存、销售、退货、班次、采购、报表和员工权限形成稳定日常流程，错误可恢复、操作可追溯。
3. **长期目标：AI 增强经营**——在可信的门店数据之上，提供自然语言查询、酒款推荐和可解释的补货/定价建议；所有写入动作由人审核确认。

### 本阶段验收指标

- **正确性：** 测试销售、支付、退款、库存和班次结果能与 Odoo 对账；任何时点只写入 Odoo 这一业务事实源。
- **可靠性：** Orithos 登录和 Odoo 会话恢复路径明确；连接失效时给出可操作提示，不静默显示过期数据。
- **可用性：** 收银、商品、销售历史、关账等试点页面完成真实浏览器操作验收，标记通过/失败/未测及证据；仅 HTTP 200 不算通过。
- **诚实性：** 未接 Odoo 的本地示例设置明确标为示例或只读不可用，不允许被误认为线上真实税率、支付方式或门店配置。
- **AI 边界：** 先只读、可解释、可降级；采购、改价、退款和销售等写操作必须由用户明确确认。

### 决策原则

- Odoo 是唯一业务事实源；Classic MySQL 不参与线上业务双写。
- 生产写操作限定在已确认的测试对象，销售、退款、关账、采购确认和现金调整每次分别复核。
- AI 先查询和建议，不能绕过权限直接创建订单、退款、采购或改价。
- 若演示班次/DEMO 商品无法安全隔离，暂停交易 UAT，改用独立测试数据库或复制环境，不污染真实账。

### 阶段 1：完成受控收银闭环（P0）

**前置条件**

- 只使用交接文档记录的测试班次 `orithos_store1/00003` 和两款 DEMO 酒测试库存。
- 开始前确认 POS 班次中没有非测试交易。测试班次已在生产 Odoo 中打开，关账前需复核订单和支付记录。
- 实际结账、退款或关账前，先向店主说明将写入的内容并获得针对该次操作的明确确认。既有“最高权限”不能替代交接文档要求的交易前核对。

**工作项**

1. 只读检查两款酒的价格、税、库存、包装单位、当前 POS 班次和支付方式。
2. 店主确认后，使用小额 DEMO 商品完成一笔 Card 和一笔 Cash 测试销售，检查金额、GST、包装数量、支付状态和收据。
3. 在销售历史定位刚刚生成的指定测试单，核对详情；确认后仅对该测试单执行退款并检查 Odoo 结果。
4. 汇总班次所有测试销售、退款和现金记录；店主确认无遗留后执行关账。
5. 对账 Orithos 页面与 Odoo 中的订单、支付和班次结果，记录问题并修复后复验。

**完成条件**

- Card/Cash 订单、收据、历史详情与 Odoo 记录一致。
- 指定测试单退款金额、状态和原因正确，未影响其他订单。
- 班次现金差异符合预期并已解释，关账成功。
- 测试班次结束后恢复安全状态；不得把 DEMO 销售当成真实经营数据。

- 逐页记录结果：通过、失败、未测和依赖数据，不以 HTTP 200 作为业务验收。
