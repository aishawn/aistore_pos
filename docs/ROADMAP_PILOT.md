# Orithos POS 后续目标与实施计划

基于 [交接文档](HANDOFF_2026-10-13.md) 制定。本文用于指导从当前试点状态走向可控门店试用；进度与线上事实以 Dokploy、Odoo 和 POS 实测为准。

## 产品目标

为澳洲独立酒类零售店提供简洁、可靠的 POS 和日常经营工作台：店员能快速完成收银，老板能掌握商品、库存、采购和销售，并逐步借助 AI 改善补货、定价和推荐。

### 试点目标

让一位店主和少量店员，在不重复录入、不污染正式业务账的前提下，完成一条可追踪的核心流程：

**登录 → 读取 Odoo 商品与库存 → 收银 → 订单/收据 → 销售历史 → 指定订单退款 → POS 班次关账**

Odoo 是业务数据唯一事实源。Orithos 负责简洁交互和增值能力，不与 Classic MySQL 双写。

## 成功标准

### 试点可用（当前最近目标）

- Dokploy 当前运行版本与 GitHub `main` 的部署提交可核对，关键页面通过生产冒烟检查。
- Orithos 登录后 Odoo 会话可以可靠建立；服务账号自动恢复在配置后通过失效 Cookie 场景验证，未登录用户不能借此访问。
- 商品价格、库存、销售单、支付记录和班次信息均以 Odoo 数据为准。
- 经批准的测试班次能完成收银、查看收据和历史订单、对指定测试单退款、最后关账；过程可在 Odoo 对账。
- 不发生无意的真实销售、退款、现金调整、采购确认或正式班次关闭。

### AI 试点可用（核心 POS 稳定后）

- AI 默认关闭；配置预算和模型密钥后先做无业务数据连通测试。
- 智能查询能回答约定范围内的销售/库存问题，并执行门店权限与只读限制。
- 进货建议能说明推荐商品、数量和依据；价格建议展示来源与时间；酒款推荐只给出 Odoo 中在售且有库存的商品。
- AI 生成结果只是建议；采购、改价和交易写入必须由用户检查并确认。
- 每个功能都有可解释的回退路径；模型不可用时核心收银仍可工作。

## 实施阶段

### 阶段 0：确认版本与服务可恢复（P0）

**工作项**

1. 在 Dokploy 确认有包含 `917eeba` 或后续提交的 **Done** 部署；若无，普通 Deploy 当前 `main`，绝不使用 Fresh Volumes。
2. 配置 `ODOO_SERVICE_USERNAME` 和 `ODOO_SERVICE_PASSWORD`。先按交接文档使用现有员工账号恢复可用性；凭据只放 Dokploy Environment。之后安排最小权限专用账号替换。
3. 重新部署后，让 Orithos 保持登录、清除 Odoo Cookie，再打开 Integrations 和 POS，确认自动恢复；注销 Orithos 后确认不会恢复。
4. 按 [部署冒烟清单](../DEPLOYMENT.md) 检查 `/`、`/close`、Integrations、产品页和服务状态；记录部署 SHA 与结果。

**完成条件**

- Dokploy 部署成功，运行 SHA 可识别。
- Integrations 清楚显示自动恢复已配置；会话失效后能够恢复，未登录访问被拒绝。
- 核心页面无阻断错误，Git push 到 Dokploy 的自动部署行为有结论（正常或已记录的手动发布流程）。

### 阶段 1：完成受控收银闭环（P0）

**前置条件**

- 只使用交接文档记录的测试班次 `orithos_store1/00003` 和两款 DEMO 酒测试库存。
- 开始前确认 POS 班次中没有非测试交易。测试班次已在生产 Odoo 中打开，关账前需复核订单和支付记录。
- 实际结账、退款或关账前，先向店主说明将写入的内容并获得针对该次操作的明确确认。既有“最高权限”不能替代交接文档要求的交易前核对。

**工作项**

1. 只读检查两款酒的价格、税、库存、包装单位、当前 POS 班次和支付方式。
2. 店主确认后，使用小额 DEMO 商品完成一笔 Card 和一笔 Cash 测试销售，检查金额、GST、包装数量、支付状态和收据。
3. 在销售历史定位刚刚生成的指定测试单，核对详情；确认后仅对该测试单执行退款并检查 Odoo 结果。
4. 汇总班次所有测试销售、退款和现金记录；店主确认无遗留后执行关账。
5. 对账 Orithos 页面与 Odoo 中的订单、支付和班次结果，记录问题并修复后复验。

**完成条件**

- Card/Cash 订单、收据、历史详情与 Odoo 记录一致。
- 指定测试单退款金额、状态和原因正确，未影响其他订单。
- 班次现金差异符合预期并已解释，关账成功。
- 测试班次结束后恢复安全状态；不得把 DEMO 销售当成真实经营数据。

### 阶段 2：门店日常管理验收（P1）

按只读页面优先，写操作仅用明确的测试数据：

- 商品、客户、供应商列表/搜索/详情，以及库存和售价的一致性。
- 采购单、补货建议、报表的空状态、错误状态、门店权限和数据范围。
- 补货审批只能创建草稿 RFQ；核实草稿后再由店主决定是否确认采购。
- 登录刷新、重新登录、登出、保护路由，以及 Odoo 会话失效恢复。
- 逐页记录结果：通过、失败、未测和依赖数据，不以 HTTP 200 作为业务验收。

**完成条件**

- 试点涉及页面均有可复现的验收记录。
- 所有阻断问题有修复提交或明确负责人/后续方案。
- 没有把未实现功能、空状态或模拟数据描述为已上线能力。

### 阶段 3：AI 小范围验证（P1，需预算批准）

**顺序**

1. 明确模型、调用费用预算、数据边界、日志保留和失败降级方案；未确认前保持 `AI_ENABLED=false`。
2. 做不带客户/交易隐私数据的模型连通与延迟验证。
3. 优先试点只读自然语言查询：限定报表视图、门店权限、行数和只读 SQL；问题无法安全回答时说明原因。
4. 试点酒款推荐：从 Odoo 读取商品、价格、库存与可用商品属性，验证库存过滤和推荐解释。
5. 再评估进货建议、公开价格比较、语音和图片识别。将建议与执行分开，未经用户确认不写采购单、改价或交易。

**完成条件**

- 每个 AI 场景有明确输入、输出、权限和错误回退验收案例。
- 查询不能越权或写数据；建议给出可核对依据；AI 失败不影响 POS。
- 费用在约定预算内；店主确认试点结果后才扩大使用范围。

### 阶段 4：扩大实际使用（P2，试点复盘后）

根据真实试用反馈再排期：离线收银、挂单跨设备同步、赊账/拆分支付、多价目表与汇率、促销价单、Manage Cash 对接 Odoo、更多门店和员工权限。

不要在核心交易和数据对账稳定前并行扩张这些功能，以免增加验收面和账务风险。

## 运行与数据原则

- Odoo 是唯一业务事实源；不对 Classic MySQL 双写。
- 测试班次、库存、销售与退款都是真实写入 Odoo 的数据，执行前先核对对象和影响范围。
- 不清空生产数据库/数据卷，不使用 Fresh Volumes，不创建未经批准的采购、支付、退款或现金调整。
- 所有密钥、密码和令牌只进 Secret/环境配置，不进 Git、日志或交接材料。
- 每次部署记录提交 SHA、Dokploy 结果和冒烟检查；每次交易验收记录使用的测试单与最终状态。
- 版本、库存、班次和部署状态可能变化；开始每个阶段前先实测，必要时更新 [交接文档](HANDOFF_2026-10-13.md)。
