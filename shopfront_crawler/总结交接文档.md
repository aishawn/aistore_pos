## 1. 系统边界

```text
Shopfront -> shopfront_crawler 自有数据库 -> POS/Odoo 集成 API -> skr.orithos.com.au Sell
```

crawler 不直连 Orithos MySQL，也不绕过业务 API 写生产表。商品、库存和正式销售必须经过门店映射、商品匹配、完整性和幂等校验。

业务约束：

- 商品匹配优先条码，SKU 兜底；不能按名称自动创建或匹配正式商品。
- 缺少稳定 Sale ID、完整销售行或支付信息时，只保存 crawler 数据并报警，不创建正式销售。
- 历史销售导入不重复扣库存；库存以 Shopfront 当前快照为准。
- 图片、品牌等字段如果 Shopfront 源端为空，保持为空，不人工伪造。

## 6. 历史任务完成后的唯一操作顺序

确认 `job 30` 完成且没有任何 active job 后：

1. 执行一次销售行修复：

```powershell
Invoke-RestMethod "https://shopfront.orithos.com.au/api/stores/skr/pos/sales-repair" -Method Post
```

2. 等待 repair 完成，再检查：

```powershell
Invoke-RestMethod "https://shopfront.orithos.com.au/api/pos/coverage?store=skr" | ConvertTo-Json -Depth 12
```

目标是 `sale_items_missing_name` 降到 0，或仅剩 Shopfront 源端确实没有名称的记录。

3. 执行一次商品/库存快照：

```powershell
Invoke-RestMethod "https://shopfront.orithos.com.au/api/stores/skr/pos/catalog-snapshot" -Method Post
```

4. 等待完成后，只读抽查 Sell/Odoo：商品名称、描述、分类、品牌、条码、SKU、价格、成本、税率、图片、库存、销售行名称、支付和销售汇总。不创建真实测试销售。

## 7. 每日同步规则

生产任务使用门店本地时间 `02:00 Australia/Adelaide`，每天重新同步最近 3 个营业日，覆盖销售修改、取消、退款、延迟上传、商品和当前库存。Webhook 只负责缩短发现延迟，完整数据由 crawler 主动拉取。

应保留每个分片的状态、请求次数、错误、重试时间和数据范围，以及每条外部记录的来源 ID、`raw_payload`、导入状态和错误。未匹配条码和缺失销售明细进入待处理清单。

## 9. 故障排查

- 历史任务不推进：先查 `status`、`runs` 和 Dokploy crawler 日志；不要重复提交。
- 服务重启：确认数据库卷仍在，检查任务是否由持久化游标续跑；不要 Fresh Volumes。
- Sell 商品有名称但销售行缺名称：等待历史完成，再按“sales-repair -> coverage -> catalog-snapshot”执行。
- 未匹配条码：进入人工映射清单，禁止按名称自动匹配。
- 图片/品牌为空：检查 Shopfront raw payload 和 API 权限；源端为空时保持为空。
- 线上版本异常：检查 Dokploy 构建提交、启动日志和 `/healthz`，不要只依据 Git 提交号判断已部署。
