## 6. 历史完成后的唯一操作顺序

1. 确认 job 30 完成且无其他 active job。
2. 只执行一次销售行修复：

```powershell
Invoke-RestMethod "https://shopfront.orithos.com.au/api/stores/skr/pos/sales-repair" -Method Post
Invoke-RestMethod "https://shopfront.orithos.com.au/api/pos/coverage?store=skr" | ConvertTo-Json -Depth 12
```

3. 修复完成后只执行一次目录/库存快照：

```powershell
Invoke-RestMethod "https://shopfront.orithos.com.au/api/stores/skr/pos/catalog-snapshot" -Method Post
```

4. 只读核验 Sell：商品名称、条码、价格、库存、历史销售行名称和汇总差异。不创建真实测试销售。

## 7. 每日同步与并发

每日在门店本地时间 `02:00 Australia/Adelaide` 执行，重新同步最近 3 个营业日，覆盖销售修改、取消、退款、延迟上传、商品和当前库存。

已部署的并发保护：

- 手动同步遇到门店 active job 返回 `409`；
- catalog snapshot 检查门店所有 active job；
- 每日调度遇到历史、快照或修复任务时跳过该门店；
- 历史分片完成后提交事务，重启可从持久游标继续；
- Webhook 只触发发现，完整数据由后台拉取并快速返回 2xx。

## 8. 正式销售导入规则

必须同时满足：稳定 Sale ID；完整商品行和支付；条码优先、SKU 兜底匹配；门店/company/outlet 映射通过；重复外部 ID 只更新。缺少完整明细时只保存汇总并报警，不得伪造正式销售。取消、退款使用可审计状态或退款模型，不删除销售。未匹配商品进入待处理清单，禁止按名称自动创建。

## 10. 故障排查

- 任务不推进：先查 status/runs，再看 Dokploy crawler 日志；不要因单个 14 天分片耗时较长而重复提交。
- Sell 商品有名称但销售行缺名称：历史完成后按“sales-repair -> coverage -> catalog-snapshot”执行。
- 线上 500 或授权丢失：检查 healthz、运行时版本、数据库卷和启动迁移；不要删除数据卷。
- GitHub 提交号不能单独证明线上版本，需用 Dokploy 记录、启动日志或线上行为确认。
