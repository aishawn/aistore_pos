## 1. 项目定位

```text
Shopfront
  -> shopfront_crawler 自有数据库
  -> crawler 只读 API / POS 集成 API
  -> Orithos POS/Odoo
  -> https://skr.orithos.com.au
```

当前首个门店：`store_key=skr`，Shopfront vendor=`skr`，门店时区=`Australia/Adelaide`。

边界规则：

- crawler 不直连 Orithos MySQL，不绕过业务 API 写生产表。
- 商品匹配按条码优先、SKU 兜底；不按名称自动创建或匹配正式商品。
- 缺少稳定 Sale ID、完整销售行或支付信息时，只保存 crawler 数据并报警，不导入正式销售。
- 历史销售导入不重复扣库存；库存以 Shopfront 当前库存快照覆盖。
- Shopfront 源端没有图片或品牌时保持为空，不伪造数据。
- 同一个外部 Sale 重跑必须 update/upsert，不能产生重复 POS 销售。

## 9. 每日同步

生产调度为门店本地时间每天 `02:00 Australia/Adelaide`，重新同步最近 3 个营业日，覆盖销售修改、取消、退款、延迟上传、商品和当前库存。Webhook 只作为实时触发器，完整 Sale/Product 仍由 crawler 主动拉取。

每次运行应可追踪：门店、时间范围、请求次数、重试、销售/商品/库存数量、POS 创建/更新/失败数量和错误原因。服务重启后依靠持久化任务状态和游标继续，不要以进程内 `running` 状态作为唯一真相。

## 10. 排障规则

- 任务不推进：先查 `status`、`runs` 和 Dokploy 日志；不要重复提交历史任务。
- 任务显示完成但下游数量不足：确认线上镜像是否包含 `e65ed908`，并检查该分片的 POS/Odoo 导入结果。
- Sell 有商品名但销售行缺名：历史完成后按“sales-repair -> coverage -> catalog-snapshot”执行。
- 未匹配条码：进入人工映射清单，禁止按名称自动匹配。
- 图片/品牌为空：检查 Shopfront 原始 payload 和 API 权限；源端为空时保持为空。
- 服务重启：确认数据库卷仍在、任务游标存在；不要 Fresh Volumes。
- 线上版本异常：检查 Dokploy 构建提交、启动日志和 `/healthz`；不要只看本地 Git 提交号。
